# Support matrix — claims must link to evidence

Generated by hand at M0. Document 07: "Release claims are generated from this matrix and its
passing gate IDs, not from the presence of flags." Every row's initial status is
NOT IMPLEMENTED, never supported, and a capability probe alone proves kernel availability, not
full-model quality or performance.

**Nothing in this repository executes a model.** Six rows now name a checkpoint, and none of them
is model support: task 0018 **imported** tensors that nothing runs, task 0020 **read** expert bytes
that nothing computed with, task 0021 **computed** with a real layer's expert weights, task 0023
computed with **every routed layer's** — the designated artifact's entire 45,675,970,560 B expert
payload — task 0024 **imported** two more artifacts' asymmetric INT4 weights that nothing ran, task 0025
**repacked** one of those modules into a canonical artifact that nothing ran either, and task 0028
**executed** that republished module — the first canonical INT4 tensor this repository computes with;
the computing was all of it over **synthetic activations and routes written by their tests**. A layer that
matches its own reference on invented input says nothing about what the model would produce, and
neither do thirty of them, nor does one projection of one layer whose weight happens to be real; that is O2, and it needs paired output against the released model. The
88.5% of that artifact which has now moved through the engine is exactly the 88.5% that is experts:
its attention tower, embedding and norms have not, and nothing composes a routed block into a graph
that generates a token. The remaining gates below are toolchain, format and enforcement
gates. Reading any of them as model support would be exactly the substitution this matrix exists to
prevent.

## What the passing rows do not mean

- A passing host decode gate means the reconstruction equation is right for synthetic tensors. It
  does not mean any of the ten [candidate checkpoints](quantization-candidates.md) can be loaded:
  their tensor headers, zero-point packing, activation-order maps and exclusion lists are
  uninspected at the byte level.
- The task 0005 smoke cases remain toolchain probes. `G-BF16-DEVICE-CHAIN` additionally qualifies
  the narrowly named synthetic BF16 operations, shapes and SM images above. It does not qualify a
  checkpoint, model graph, attention/state path, actual context, generation, quality or throughput.
- A passing capacity gate means this machine and three GPUs answered a question about themselves and
  the ledger admitted a plan against the answers. Task 0010 separately proves one small admitted
  device arena allocates; the capacity probe itself still allocates no payload and proves no plan
  execution. Either capacity figure can change a second later. The host figure in particular is
  `MemAvailable`, which includes cache the kernel expects to reclaim.
- A passing ledger gate means the accounting arithmetic and refusal rules are right for supplied byte
  counts. The selected-chain gate derives and admits one synthetic graph's exact weight,
  activation, workspace, retained upload-source and final-output envelope and materializes the
  device ranges in one allocation. It has no reusable residency pipeline, host cache, state,
  attention or model run.
- `G-HOST-NODRIVER` means host CI can run anywhere. It is not evidence about any device, and
  document 07 forbids reading it as such.
