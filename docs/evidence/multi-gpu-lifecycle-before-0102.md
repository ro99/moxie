# Current multi-GPU dense lifecycle (base 50464e9)

Fact inventory only. Line references below are repository-relative. The ordinary successful one-row decode path is described first; refusal/drop alternatives are separated. “Admission” in the counts means a call to `SelectedReservedPlan::admit`, not startup admission of the persistent paged runs.

## TP2: one `DenseRankWorkers::execute_dense`

**Persistent owner before the call.** `DenseRankWorkers::spawn` starts two rank threads and command channels (`dense_tp_workers.rs:253-269`). Each rank acquires one `RankContext`, peer-access grant, stream and measured `Ledger`, creates one `DeviceKvSequence`, and admits `PagedAttentionRun` objects once for its configured state layers (`dense_tp_workers.rs:1233-1265,1347-1405,1458-1524`). It also admits a per-rank 144 MiB `CollectiveBuffers` NCCL reserve and initializes one communicator (`dense_tp_workers.rs:1406-1443,1527-1537`). `WorkerState` retains context/stream, ledger, state, runs, communicator and reserve across calls; `held`, transaction and join temp are step-local fields (`dense_tp_workers.rs:203-228,1422-1434`). There is no `DensePlanSet` in these worker paths: stages call ordinary `SelectedReservedPlan::admit` (`dense_tp_workers.rs:2111-2118`).

**Successful command order, identically paired to rank 0 and rank 1.** `pair_command` sends the two commands, waits for both replies, and checks their rank declarations/status before returning; it is a host rendezvous after *each* listed command (`dense_tp_workers.rs:766-851,1598-1616`).

1. `Begin`: check/observe idle attention runs, begin a transaction in each rank's persistent state, and admit/create a device `Activations` boundary arena for this call (`dense_tp_workers.rs:528-550,1884-1906,2035-2068`).
2. For every `Stage::Replicated(range)` in the supplied `TensorParallelLowering`, and for **each node** in that range: build a one-node `StageGraph` on the coordinator, invoke the caller's bindings callback once per rank, then send `Stage(keep=Some(original output))`, `Drain`, `ClosePlans`, in that order (`dense_tp_workers.rs:552-594`). Worker `Stage` lowers that graph with `lower_selected_ordered`, admits one selected plan, copies any prior boundary input device-to-device, executes the graph, waits for the completion lease, and copies the node output into the per-step boundary arena (`dense_tp_workers.rs:2072-2183,1916-1932,2855-2885`). `Drain` waits for NCCL Ready then a newly recorded CUDA stream event; `ClosePlans` closes/releases the stage plan from the same ledger (`dense_tp_workers.rs:1753-1825,1934-1940,2813-2826`).
3. For every `Stage::Local { nodes, join }`: build two rank-specific `StageGraph`s from the rank partitions, get bindings per rank, send `Stage(keep=None)`, then `JoinPrepare`, `JoinCopy`, `JoinDrain` (`dense_tp_workers.rs:596-695`). `Stage` again lowers/admits one plan per rank and synchronously finishes its dense lease, but holds that plan so the join can read its output (`dense_tp_workers.rs:2072-2183`). `JoinPrepare` admits a fresh `CollectiveBuffers` temp arena with status/data/dummy ranges, takes a joined-output range from the step boundary arena, and loads a conversion module for a Reduce join (`dense_tp_workers.rs:2186-2315`). `JoinCopy` writes the status word then enqueues grouped status all-reduce plus data all-reduce or gather on each rank's stream (`dense_tp_workers.rs:2318-2435`). `JoinDrain` waits for NCCL Ready and stream completion before reading status; on success it converts FP32 sum to BF16 or interleaves gathered rows, drains again, returns the source to its plan, stores joined output in the boundary map, closes temp ranges/arena/module and closes the source stage plan (`dense_tp_workers.rs:2437-2628`). The host waits for paired `JoinDrain` before starting another stage (`dense_tp_workers.rs:682-695`).
4. After the stage loop, send `ReadOutput` to **both** ranks, copying the output boundary range to a host `Vec<u8>`; the coordinator returns the bytes from rank 0 (`dense_tp_workers.rs:699-721,1979-1997`). Then `settle(false)` sends `Drain`, `Cleanup`; cleanup reclaims drained leases and attention ranges, closes any remaining plans, releases boundary values, closes its arena and ledger charge (`dense_tp_workers.rs:721-729,740-750,2631-2731`). `execute_dense` returns `DenseWorkerStep` holding two still-open transactions and host logits; KV publication has not happened (`dense_tp_workers.rs:1108-1122`).
5. Calling `DenseWorkerStep::commit` later sends one `Commit` command per rank (`dense_tp_workers.rs:1124-1135,953-987`). Inside each worker, that command has paired prepare and apply rendezvous; `prepare_commit` checks the per-rank state/runs, then `apply_commit` uses the persistent runs as paged writers and clears the rank transaction (`dense_tp_workers.rs:1627-1732`). Dropping the step instead sends the settling `Drain`, `Cleanup`, and `Abort` commands if still live; an error during `execute_dense` also settles/aborts when the group is not lost (`dense_tp_workers.rs:731-763,1139-1144`). `Stats` is diagnostic, not part of an ordinary step; `ClosePrepare`, `CloseDestroy`, `CloseRelease`, `Shutdown` are worker-group close commands, not per-step commands (`dense_tp_workers.rs:862-869,908-950`).

**Weights and KV.** The API receives a caller callback producing `OwnedBinding` host bytes for each rank/stage (`dense_tp_workers.rs:515-525,570-578,610-628`). In the Shape A device fixture, the callback maps each stage weight back to the fixture's host weight, applies the declared rank slice/rows, encodes bytes and returns a weight binding every invocation (`dense_tp2_device.rs:825-903,1270-1277`). The worker's ordinary selected admission charges a plan-local `PackedResidentWeights` region (plus activation/workspace regions); `execute_dense_stage` owns the bindings for the operation, and `upload_sources` enqueues a host-to-device copy of every supplied source, including weights, to that new plan's range (`chain.rs:256-273,345-385,1407-1464`; `dense.rs:146-165,253-269,2493-2519`). At finish the weight host bindings attach to that *plan*; closing the plan at replicated `ClosePlans` or local `JoinDrain` ends that plan's weight residency (`dense.rs:442-451`; `chain.rs:762-773`; `dense_tp_workers.rs:590-593,2620-2621`). Thus the callback can source bytes from a long-lived host fixture, but rank-device weights are admitted and uploaded again for each applicable stage on each decode call. Between stages, activations retained in the boundary arena are copied device-to-device into the next plan; those are not host bindings (`dense_tp_workers.rs:2132-2139,2855-2885`). Each rank's `DeviceKvSequence` and its one run per configured local layer remain in `WorkerState` across steps; a stage with attention borrows the persistent state/runs and maps stage-local attention nodes to rank-local state layers, while a stage with no state layers passes an empty run slice (`dense_tp_workers.rs:220-221,2147-2167`). Only commit publishes the rank's pending KV rows (`dense_tp_workers.rs:1646-1715`). The state/runs and NCCL reserve are released on group close, after per-step resources are gone (`dense_tp_workers.rs:1827-1874,2742-2768`).

**Shape A TP2 decode admission count.** Shape A has six dense layers (`moxie-cli/src/gemma.rs:22-27,43-77`). The model graph has embedding; in each layer, attention head chain, output projection and GeGLU MLP; and final norm plus vocab projection (`moxie-models/src/gemma4.rs:557-564,566-805,808-823`). TP lowering makes each attention chain, output projection, MLP and final vocab projection a Local span; other nodes form Replicated spans (`moxie-plan/src/tensor_parallel.rs:563-590,592-670,753-810,859-874`). That is 6×3+1 = **19 Local stages** and 1 embedding + 6×(attn norm, attn-out norm, residual, FFN norm, FFN-out norm, residual) + 1 final norm = **38 replicated nodes**. The executor sends a separate `Stage` for each replicated node (`dense_tp_workers.rs:559-579`), hence **57 selected-plan admissions per rank, 114 across TP2, per one-row decode call**. There are 19 paired `JoinDrain` barriers and 38 paired replicated `Drain`/`ClosePlans` barriers, in addition to the finish/readback/settle barriers.

## Pipeline: one `PipelineWorkers::execute`

`PipelineWorkers` holds at least two stage workers. Stage 0 may be a TP pair; all later stages are solo workers. These workers are spawned separately and persist across `execute` calls (`pipeline.rs:16-26,46-79`). Each solo owner thread acquires its own context/stream/ledger, creates a stage-local `DeviceKvSequence`, and admits its configured `PagedAttentionRun` vector at startup; those stay in `WorkerState` between calls (`rank_worker.rs:281-290,512-556`; `dense_tp_workers.rs:1458-1524`). Solo workers have no NCCL communicator (`rank_worker.rs:281-290`).

At entry the pipeline verifies the lowering against the source graph, then **builds every pipeline `StageGraph` anew** from the pipeline cuts; if stage 0 is a pair it also re-lowers that stage graph for TP2 (`pipeline.rs:114-188`). For a pair stage, it invokes the TP2 `execute_dense` sequence above once (exactly one microbatch is required) and takes the pair's output as an owned host byte vector (`pipeline.rs:157-162,198-235`). The wavefront loop is sequential (`pipeline.rs:237-265`). For each solo stage/microbatch it calls the user bindings callback for that stage, adds the prior stage's owned host output as a new handoff `OwnedBinding` when stage > 0, and sends one solo `WorkerCommand::Step` with cloned stage graph, catalogue, bindings, row count and absolute visible-token endpoint (`pipeline.rs:368-436`; `rank_worker.rs:34-48,98-123`). There are no separate solo Begin/Drain/Cleanup commands: inside `Step`, the worker lowers with `lower_selected_ordered`, admits one ordinary `SelectedReservedPlan`, begins a state transaction on its first step if needed, executes and finishes the dense lease (including host output readback), then closes/releases the plan before replying (`rank_worker.rs:292-415`; `dense.rs:360-451`). Its weight bindings are plan-local host bytes and are uploaded through the same `upload_sources` path on every `Step` (`pipeline.rs:382-386,430-436`; `dense.rs:2493-2519`). The stage output becomes host `Vec<u8>` and the next stage receives it via a host binding; `handoff_bytes` records each boundary's copied byte count (`pipeline.rs:266-297,389-425`). Each synchronous solo `Step` reply and the sequential wavefront are host barriers; the pair variant also has TP2's per-stage paired rendezvous and `JoinDrain` barriers (`pipeline.rs:237-265`; `dense_tp_workers.rs:766-851`).

`PipelineWorkers::execute` returns a `PipelineStep` with host logits, handoff byte counts, and open per-stage transactions (`pipeline.rs:310-317,37-44`). `PipelineStep::commit` sends `PrepareCommit` to each solo stage in order, commits the TP pair if present, then sends `ApplyCommit` to each solo stage in order; solo `apply_commit` publishes through its persistent state/runs and clears the transaction (`pipeline.rs:474-514`; `rank_worker.rs:125-139,417-465`). Error/drop sends `Abort` to solos and drops the pair step, which aborts its two rank transactions (`pipeline.rs:439-461,517-531`; `rank_worker.rs:141-144,468-474`; `dense_tp_workers.rs:1139-1144`). Solo `Stats` and `Shutdown` are diagnostic/worker-close commands; shutdown closes persistent runs and checks the ledger (`rank_worker.rs:146-149,161-182,485-509,570-595`). `PipelineWorkers::close` closes the pair and solos, not during an ordinary step (`pipeline.rs:349-365`).

For a **two-solo-stage PP one-row decode** with one microbatch, the command order is solo 0 `Step`, then solo 1 `Step` with host handoff; `commit` later sends solo 0 `PrepareCommit`, solo 1 `PrepareCommit`, solo 0 `ApplyCommit`, solo 1 `ApplyCommit`. It makes **two selected-plan admissions total, one on each GPU**, per decode step (`pipeline.rs:237-265,368-436,474-514`; `rank_worker.rs:320-336`). For `m` microbatches on two solo stages it is `2m` admissions. In the supported two-stage **TP2+solo** variant, the pair stage invokes its TP substage sequence once and the solo stage invokes one `Step`; for the Shape A example cut after layer 2 (`dense_tp2_device.rs:1816-1841`), the pair subgraph has 3×3 = 9 Local spans and 1+3×6 = 19 replicated one-node commands, or **28 admissions per TP rank plus one solo admission = 57 total** for one decode microbatch (`pipeline.rs:198-235,368-436`; `dense_tp_workers.rs:559-695`).
